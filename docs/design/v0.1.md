# eslint-plugin-nest-drift — v0.1 design

Date: 2026-09-26
Status: draft, pending review

## Problem

In NestJS codebases the same shape is described several times: the TypeScript type of a DTO property,
the `class-validator` decorators that validate it at runtime, the `class-transformer` decorators that
instantiate it, and the `@nestjs/swagger` metadata that documents it. Nothing checks that these agree.
TypeScript is satisfied by `@IsString() amount: number`, the app compiles, and invalid data reaches
business logic.

## Goal

An ESLint plugin (typed linting) that reports **semantic** mismatches between decorators and the
declared TypeScript type of a class property. It runs in the IDE through the standard ESLint extension
and in CI through `eslint`. Success criterion: on a real NestJS project it finds real mismatches with
**zero false positives** in the recommended config.

## Non-goals (v0.1)

- Presence/style rules already covered by `@darraghor/eslint-plugin-nestjs-typed` (missing decorators,
  `@IsOptional` vs `?`, `@ApiProperty({required})` vs `?`, `@ValidateNested` without `@Type`,
  arrays without `each`). README recommends installing both.
- Type-guard completeness (`isX(v): v is X`) — v0.2.
- Entity ↔ DTO drift — v0.3.
- Autofixes — later, only where the fix is unambiguous.
- ESLint < 9 / legacy `.eslintrc` config.

## Distribution

- npm package `eslint-plugin-nest-drift` (name verified free on 2026-09-26), MIT license.
- Public repo `github.com/kerimakmyradov/eslint-plugin-nest-drift`.
- The `recommended` config sets `files: ['**/*.ts', '**/*.mts', '**/*.cts']` so typed rules never run on JS config files.
- Usage:
  ```js
  // eslint.config.mjs
  import nestDrift from 'eslint-plugin-nest-drift';
  export default [
    // ...typescript-eslint config with parserOptions.projectService: true
    nestDrift.configs.recommended,
  ];
  ```

## Rules (v0.1)

All rules require type information and resolve the property type through the TypeScript checker,
so aliases, unions, `| null`, `| undefined`, arrays and enums are handled.

| Rule | Reports | Example |
|---|---|---|
| `validator-matches-type` | A primitive `class-validator` decorator whose checked kind does not match the property type. | `@IsString() amount: number` |
| `enum-matches-type` | `@IsEnum(E)` (E: enum, const object or `as const` array) where the property type and the enum values differ in either direction (a plain `string` / `number` property of the same kind as the values is accepted) (compared by runtime value, so `'open'` equals `Status.Open`; the enum → property direction only when all enum values are literals), e.g. `status: Status.Closed` with `@IsEnum(Status)`; `@IsIn([...])` literals not assignable to the property type. | `@IsEnum(Status) currency: Currency` |
| `nested-type-matches` | `@Type(() => X)` where the instance type of `X` is not assignable to the property type. For arrays / `Set` / `Map` the element type is compared; built-in constructors (`Number`, `String`, `Boolean`, `Date`) are compared by kind; `@Type` with a second argument (discriminator) is skipped. | `@Type(() => Foo) bar: Bar` |
| `each-matches-array` | `{ each: true }` on a property whose type contains no collection (array, tuple, `Set`, `Map`); or a single-value validator (primitive validators, `IsObject`, `IsEnum`, `IsIn`) without `each` on a property whose every non-nullish constituent is a collection. Mixed unions like `string \| string[]` are never reported. | `@IsString({ each: true }) tag: string` |
| `api-property-matches-type` | `@ApiProperty`/`@ApiPropertyOptional` with `type`, `enum` or `isArray` contradicting the TS type. `string` and `Date` are interchangeable (JSON dates); a missing `isArray` on an array is left to darraghor. | `@ApiProperty({ type: Number }) id: string` |
| `nullable-matches-type` | Type includes `null` but no decorator permits null (`@IsOptional`, `@ValidateIf`, or `@ApiProperty({ nullable: true })` for the swagger variant); or `nullable: true` on a non-nullable type. | `@IsString() note: string \| null` |

### Validator → expected kind table (`validator-matches-type`)

| Decorators | Accepted TS kinds |
|---|---|
| `IsString`, `IsUUID`, `IsEmail`, `IsUrl`, `IsISO8601`, `IsDateString`, `IsNumberString`, `IsDecimal`, `Length`, `MinLength`, `MaxLength`, `Matches` | `string`, string literal, string enum |
| `IsNumber`, `IsInt`, `IsPositive`, `IsNegative`, `Min`, `Max` | `number`, number literal, numeric enum |
| `IsBoolean` | `boolean`, boolean literal |
| `IsDate`, `MinDate`, `MaxDate` | `Date` |
| `IsArray`, `ArrayMinSize`, `ArrayMaxSize`, `ArrayNotEmpty` | array / tuple |
| `IsObject` | non-primitive object |

Kind-agnostic decorators (`IsNotEmpty`, `IsDefined`, `IsOptional`, `ValidateIf`, `Allow`, `Equals`, …) are not checked.

Type classification details:
- An intersection of a primitive with object types (branded types such as
  `number & { __brand: 'Money' }`) is classified as that primitive.
- `bigint` is its own kind: not accepted by `IsNumber`/`IsInt` (class-validator rejects bigint at runtime).
- Template literal types (`` `${number}` ``) are classified as `string`.
- Class instance types other than `Date` (e.g. `Decimal`) are `object`; a primitive validator on them is
  reported, since class-validator would reject the instance at runtime.

A property passes when every non-nullish constituent of its type is accepted
(`null`/`undefined` are delegated to `nullable-matches-type` and darraghor). With `{ each: true }`
the element type is checked instead. If the property is an array and the decorator has no `each`,
`validator-matches-type` stays silent and `each-matches-array` reports it (one report per mistake).

### Silence rules (false-positive guards)

A rule reports nothing for a property when:
- the resolved type is `any`, `unknown`, or an unresolved type parameter;
- the decorator is not imported from `class-validator`, `class-transformer` or `@nestjs/swagger`
  (resolved through the import declaration, so local re-exports and aliases like
  `import { IsString as S }` still work, and custom decorators are ignored);
- the property is not declared in a class body (properties inherited from a base class or from
  `PartialType(...)`/`PickType(...)` mixins are checked where they are declared, not in subclasses).

## Architecture

```
src/
  core/                 public engine, exported as `eslint-plugin-nest-drift/core`
    decorators.ts       decorator discovery: name, source module, call args (as AST + evaluated literal/option object)
    type-compare.ts     type classification: kinds of a ts.Type, nullish stripping, array element, enum membership
    create-rule.ts      RuleCreator wrapper; asserts typed linting is enabled with a clear error
  rules/                one file per rule, each < ~150 lines, uses only core/
  configs/recommended.ts  all six rules at "error"
  index.ts              plugin object: meta, rules, configs
tests/
  rules/<rule>.test.ts  RuleTester (vitest) with valid/invalid cases
  fixtures/             tsconfig.json + file.ts for typed RuleTester
docs/rules/<rule>.md    what it catches, bad/good example, when to disable
```

### Pro foundation

`core/` is public API with semver guarantees from v1.0 (marked experimental in 0.x). A future
private package (e.g. `@nest-drift/pro`) depends on `eslint-plugin-nest-drift/core` and ships extra
rules/configs. No pro code, flags or license checks in this repo.

### Data flow per rule

1. Visitor on `PropertyDefinition` inside `ClassDeclaration`.
2. `core/decorators` returns known decorators with source module and parsed options.
3. `parserServices.getTypeAtLocation(property)` → `core/type-compare` classifies it.
4. Rule compares expected vs actual; on mismatch reports with a message naming the decorator,
   the expected kind and the actual type text (`checker.typeToString`).

## Testing

- TDD: invalid cases written first per rule, then implementation.
- Each rule covers: plain types, aliases, unions, `| null`, arrays, enums (string + numeric),
  inheritance (`class B extends A`), `PartialType/PickType` from `@nestjs/mapped-types`/`@nestjs/swagger`,
  aliased imports, custom decorators (must be silent), `any`/`unknown` (must be silent),
  branded primitives (`number & { __brand }`), `bigint`, template literal types, `Decimal`-like classes.
- Fixture project depends on real `class-validator`, `class-transformer`, `@nestjs/swagger` types
  (devDependencies) so decorator import resolution is realistic.
- Before 0.1.0 release: run against at least one real NestJS codebase; every report reviewed;
  any false positive → new test + fix.

## Tooling

- TypeScript, `@typescript-eslint/utils` (peer: `eslint >= 9`, `typescript >= 5.4 < 6.1`; dev TypeScript pinned to 6.0.x), flat config only. Runtime engines: Node >= 20.19.
- Build: `tsup` → ESM + CJS + `.d.ts`; `exports` map with `.` and `./core`.
- Tests: `vitest` + `@typescript-eslint/rule-tester`.
- Package manager: `npm`.
- CI (GitHub Actions): lint, typecheck, test, build and a smoke run of the built plugin on Node 22 and 24.
- Release: `changesets`; publish to npm from CI on version merge, using `NPM_TOKEN` repo secret
  (user sets it up at release time).
